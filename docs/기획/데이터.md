# 데이터

> **책임:** 놀멍봅서에서 사용하는 데이터와 API의 역할, Place/PLAY 식별 구조, 외부 Source 연결 원칙을 정의한다.
>
> 후보 선정은 `콘텐츠후보지.md`, 콘텐츠 제작 규칙은 `콘텐츠.md`, 장소별 실제 콘텐츠는 `콘텐츠/장소명.md`가 정본이다.

---

## 1. 데이터 구조

놀멍봅서의 데이터는 역할에 따라 분리한다.

```text
[여행 동선]
실제 제주 여행 일정 데이터
→ 코스 추천

[관광지 정보]
한국관광공사 관광정보 OpenAPI
→ Place 정보

[현장 경험]
놀멍봅서 자체 콘텐츠
→ PLAY / Point / Mission / Discovery / Story / CLEAR

[콘텐츠 조사]
Odii + KTO + 국가유산 + VisitJeju + 공식·전문자료
→ Reality Evidence / Story Sources
```

각 데이터의 책임을 섞지 않는다.

- 코스 데이터: 제주에서 어디를 함께 여행할지
- KTO OpenAPI: 관광지가 어떤 곳이고 실제 방문에 필요한 정보
- 놀멍봅서 콘텐츠: 도착한 장소에서 무엇을 보고 발견하며 플레이할지
- 외부 Source: Mission과 Story의 사실관계를 조사·검증하는 근거

---

## 2. Place와 PLAY

### Place

`Place`는 실제 관광지다.

예:
- 성읍민속마을
- 제주목관아
- 제주돌문화공원
- 수월봉
- 제주해녀박물관

Place가 답하는 질문:

> **여기가 어떤 곳이고 실제로 갈 수 있는가?**

### PLAY

`PLAY`는 특정 Place에서 수행하는 놀멍봅서의 현장 탐험 콘텐츠다.

PLAY가 답하는 질문:

> **여기에서 무엇을 플레이하게 되는가?**

PLAY에는 다음과 같은 자체 콘텐츠가 들어간다.

- 제목
- Game Fantasy
- 역할과 목표
- 예상 시간 / 거리 / 난이도
- START / FINISH
- Point
- Mission
- Discovery
- Story
- CLEAR

### 관계

```text
Place 1 : N PLAY
```

한 관광지에 여러 PLAY가 존재할 수 있다.

예를 들어 규모가 큰 관광지는 공식 관람코스나 완결 가능한 탐험 범위에 따라 여러 PLAY로 나눌 수 있다.

## 3. Place 식별체계

### 내부 ID

Place는 놀멍봅서가 자체 발급한 불변 ID를 사용한다.

```text
Place.id
```

구체적인 UUID/ULID 등의 형식은 현재 기술 구조에 맞게 결정하되 다음 조건을 지킨다.

1. 놀멍봅서 자체 발급
2. 전역적으로 유일
3. 생성 후 변경하지 않음
4. 외부 데이터 공급자와 독립

장소 이름이나 특정 외부 서비스 ID를 내부 Place ID로 사용하지 않는다.

### 외부 ID

KTO, Odii 등 외부 서비스의 ID는 Place와 외부 Source를 연결하는 값으로 관리한다.

개념적으로:

```text
Place
├─ id
├─ name
└─ externalIds
   ├─ ktoContentId
   ├─ odiiStids[]
   ├─ visitJejuId
   ├─ heritageId
   └─ ...
```

한 Place에 같은 Source의 ID가 여러 개 연결될 수 있다.

외부 ID가 없는 Place도 생성할 수 있어야 한다.

## 4. KTO OpenAPI

한국관광공사 OpenAPI는 **Place의 관광정보 계층**을 담당한다.

### 주요 활용 정보

API가 제공하는 범위에서 다음 정보를 사용한다.

- 장소명
- 대표 이미지
- 주소
- 좌표
- 전화번호
- 개요
- 운영시간
- 휴무일
- 주차
- 이용정보

없는 값은 임의로 만들지 않는다.

### 주요 활용 화면

#### Place Detail

Place Detail은 다음 질문에 답한다.

> **여기가 어떤 곳이고 실제로 방문할 수 있는가?**

KTO 관광정보를 보여주고, 해당 장소에 PLAY가 있다면 함께 연결한다.

```text
Place Detail
├─ 대표 이미지 / 장소명
├─ 개요
├─ 주소
├─ 운영시간 / 휴무
├─ 주차 / 이용정보
└─ 이 장소에서 할 수 있는 PLAY
```

#### PLAY Detail

PLAY Detail에서는 게임 콘텐츠가 중심이다.

다만 PLAY 시작 전에 필요한 운영시간, 입장료, 휴무, 주차 등의 관광정보는 필요한 범위에서 보여줄 수 있다.

전체 관광정보는 `[장소 정보 보기]`를 통해 Place Detail로 연결한다.

### 활용 원칙

KTO OpenAPI는 실제 서비스 기능에서 사용한다.

- 실제 API 호출 내역이 존재해야 한다.
- 사용자가 실제 화면에서 API 활용 결과를 확인할 수 있어야 한다.
- 심사용 로그만 만들기 위한 의미 없는 호출을 하지 않는다.
- 제품과 관계없는 API를 개수 채우기 목적으로 추가하지 않는다.

KTO 원본 관광정보와 놀멍봅서 자체 Mission/Story 데이터는 분리해서 관리한다.

## 5. PLAY 경로 데이터

PLAY의 탐험 경로는 놀멍봅서 자체 콘텐츠다.

```text
PLAY
├─ start
│  ├─ name
│  ├─ lat
│  └─ lng
├─ points[]
│  ├─ id
│  ├─ order
│  ├─ name
│  ├─ lat
│  └─ lng
├─ finish
│  ├─ name
│  ├─ lat
│  └─ lng
└─ route
   ├─ distance
   ├─ estimatedDuration
   ├─ revealMode
   └─ polyline?
```

### 경로 공개 방식

`FULL`
- START / Point / FINISH를 처음부터 보여준다.

`PROGRESSIVE`
- 다음 위치를 찾는 것이 게임의 일부일 때 진행에 따라 Point를 공개한다.

### 경로선

검증된 실제 보행 경로가 있을 때만 polyline을 표시한다.

실제 보행 경로를 모르는 상태에서 Point 좌표를 직선으로 연결해 걸을 수 있는 길처럼 표현하지 않는다.

필요하면 외부 지도 앱의 길찾기로 연결한다.

---

## 6. 사용자 위치

GPS는 PLAY를 보조한다.

주요 용도:
- START까지 거리
- 다음 Point까지 거리
- 지도에서 현재 위치 확인
- 외부 길찾기

GPS만으로 Mission 정답을 판정하지 않는다.

세부 Point 진행은 실제 현실 관찰과 사용자의 확인을 중심으로 한다.

위치 권한이 없어도 가능한 한 PLAY를 진행할 수 있어야 한다.

지속적인 사용자 위치 서버 전송을 기본 구조로 사용하지 않으며, 가능한 거리 계산은 클라이언트에서 처리한다.

---

## 7. 콘텐츠 Source

Mission과 Story는 하나의 외부 데이터 원문에 종속되지 않는다.

필요에 따라 다음과 같은 Source를 조사한다.

- Odii
- KTO 관광정보
- 국가유산 관련 공식자료
- 한국민족문화대백과
- VisitJeju
- 지자체 공식자료
- 관광지·박물관 공식자료
- 학술·전문자료
- 기타 신뢰 가능한 자료

Source는 크게 두 역할로 구분한다.

### Reality Evidence

> **이 Mission이 실제 현장에서 성립하는가?**

확인 대상:
- 대상의 존재
- 현재 상태
- 위치
- 일반 방문객의 접근 가능성
- 실제로 관찰 가능한 특징
- Mission Prompt와 현실의 일치 여부

### Story Sources

> **발견 뒤 설명하는 내용이 사실인가?**

확인 대상:
- 역사적 의미
- 사용 목적
- 인물과 사건
- 시대
- 생활문화
- 자연·지질적 의미

하나의 자료가 두 역할을 모두 할 수도 있지만 개념적으로는 구분한다.

---

## 8. Odii

Odii는 여러 콘텐츠 Source 중 하나다.

활용할 수 있는 용도:
- 장소 및 이야기 조사
- Reality Anchor 후보 발견
- 역사·문화·인물 정보 조사
- Story 사실관계 확인
- 다른 자료와의 교차검증

Odii의 `stid`는 Place ID가 아니다.

Odii 대본을 그대로 사용자 Story로 사용하는 것을 기본 구조로 하지 않는다.

Odii를 포함한 여러 Source를 바탕으로 사실을 검증한 뒤 놀멍봅서 자체 Story를 작성한다.

```text
Odii
+ KTO
+ 국가유산
+ 공식·전문자료
        ↓
사실 검증
        ↓
놀멍봅서 자체 Story
```

---

## 9. Story와 TTS

Story는 놀멍봅서 자체 콘텐츠다.

개념적으로:

```text
Story
├─ id
├─ title
├─ script
├─ sources[]
└─ tts
```

화면 텍스트와 TTS는 동일한 `story.script`를 원본으로 사용한다.

```text
story.script
├─ 화면 표시
└─ TTS
```

Story는 기본적으로:

> **방금 본 것 → 그것이 무엇인지 → 왜 중요한지**

순서로 전달한다.

모든 Mission에 Story가 필요한 것은 아니다.

모든 Mission에는 `Discovery`가 있고, 별도의 의미 설명이 필요한 경우 Story를 연결한다.

Story의 구체적인 작성 규칙은 `콘텐츠.md`에서 관리한다.

---

## 10. 코스 추천 데이터

코스와 PLAY는 역할이 다르다.

```text
코스
→ 제주에서 어디를 함께 여행할까?

PLAY
→ 그 장소에 도착해서 무엇을 할까?
```

기본 연결:

```text
코스
↓
Place
├─ PLAY 있음 → PLAY 연결
└─ PLAY 없음 → 관광정보
```

코스 안의 실제 LIVE PLAY는 `PLAY 가능`으로 표시할 수 있다.

향후 제작 후보 상태를 코스에서 PLAY 가능한 것처럼 표현하지 않는다.

---

## 11. 지도 데이터

지도는 다음 질문에 답한다.

> **제주 어디에서 놀멍봅서를 PLAY할 수 있고, 앞으로 어디에 추가될 예정인가?**

공개 상태는 `콘텐츠후보지.md`를 따른다.

```text
LIVE
→ 실제 PLAY 가능

PLANNED
→ PLAY 준비 중

CANDIDATE
→ 지도 비노출
```

Odii에 장소나 해설이 존재한다는 이유만으로 공개 지도에 표시하지 않는다.

---

## 12. 저장과 캐시

### 놀멍봅서 자체 데이터

다음과 같은 자체 데이터는 서비스 데이터로 관리한다.

- Place 내부 ID와 외부 ID 연결
- PLAY
- Point
- Mission
- Discovery
- Story
- Route
- 진행 상태

### 외부 API 데이터

KTO 등 외부 API 데이터의 저장·캐시는 해당 API의 이용조건과 운영정책을 따른다.

필요한 경우:
- 저장 허용 범위
- 동기화 조건
- 운영계정 정책
- 공모전 요구사항

을 확인한 뒤 적용한다.

외부 관광정보를 자체 콘텐츠와 섞어 하나의 원본처럼 관리하지 않는다.

## 13. 데이터 책임 요약

| 데이터 | 책임 |
|---|---|
| **Place.id** | 놀멍봅서 자체 관광지 식별 |
| **External IDs** | Place와 외부 Source 연결 |
| **KTO OpenAPI** | Place 관광정보 |
| **코스 데이터** | 여행 동선 추천 |
| **PLAY** | 하나의 완결된 현장 탐험 |
| **Point** | PLAY 안의 실제 이동 장소 |
| **Mission** | 현실에서 수행하는 행동·발견 |
| **Discovery** | 사용자가 확인한 사실 |
| **Story** | 검증된 Source를 바탕으로 작성한 의미 설명 |
| **TTS** | Story를 음성으로 전달 |
| **Odii** | 콘텐츠 조사 Source 중 하나 |
| **GPS** | 위치·이동 보조 |
| **지도** | LIVE / PLANNED Place 탐색 |

## 14. 문서 책임

```text
콘텐츠후보지.md
→ 어디를 PLAY로 만들 것인가

콘텐츠.md
→ PLAY를 어떻게 만들 것인가

레퍼런스.md
→ 제작 문법의 외부 근거

데이터.md
→ 데이터 / API / ID / Source 구조

콘텐츠/장소명.md
→ 실제 PLAY / Point / Mission / Story / Route
```

같은 결정은 여러 문서에 중복해서 관리하지 않는다.
